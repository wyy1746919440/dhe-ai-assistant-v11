1. 背景与目标

1.1 背景

1.0 期 AI 助手已上线，能「说」能查，但能做的动作很少。我们从 654 条运营商真实问话里做了归因，发现两类结构性问题：

  • 能力缺口：问话里有 6% 是明确的执行诉求（「帮我在南油文化广场上架康师傅碱性水」），1.0 只能答不能做。
  • 查询缺口：TOP4 问法（今日销售额 128 / 哪些机器缺货 128 / 查我的机器 73 / 怎么新增商品 44）合计占 57%，其中**「怎么新增商品」这类教学诉求**占了很大比重——因为系统里做得出来，但用户找不到入口。

⚠ 归因结论：TOP4 的高问话量主要由欢迎卡 4 个快捷按钮驱动（入口驱动），不全是未满足需求。因此本期不做「欢迎卡加经营数据卡」，而是把力气花在真正缺的能力上（详见 §3.4）。

1.2 本期目标

目标 落地方式
把高频执行诉求变成可代做 新增写能力 4 项：商品上架 / 下架 / 跨机器批量改价 / 生成补货单
把高频查询诉求补齐 新增读能力 6 张卡：补货记录 / 订单商品明细 / 按销售额反查机器 / 支付方式拆分 / 商品维度销售 / 离线原因
补知识库缺口 qa 补条目 3 项：故障排查 SOP / 商户工单兜底 / 客服管理（按载体端分路径）
把能力搬上 PC 运营商 PC 后台同一套能力，卡片字段一次给全（大屏不再折叠为副行）

1.3 边界（本期不做，见 §3.4 逐条理由）

  • 欢迎卡新增经营数据卡（移除：入口驱动，非未满足需求）
  • 音量设置写能力、缺货率门槛写能力（引导，不做写）
  • 商品库新增商品（涉及平台审核流与商品建模，无法对话闭环）
  • 远程开门（安全风险，直接触发物理门锁）
  • 技术 API / 回调问答、企业内部流程、视频监控查看、改名记录查询

2.2 为什么 OS 内部端本期维持「只说不做」

内部 OS 端的定位是内部口径问答（知识源 os_kb + 产品手册 FAQ），使用者是公司员工，操作类诉求有既定的后台流程与权限体系承接。把它开放成可执行，会引入内部越权与审计口径两类新问题，不是本期要解的事。

⚠ 澄清：本期说的「PC 端」指运营商 PC 后台，不是公司内部 OS。两者形态相似（都是右下角悬浮球 + 右侧抽屉），但使用者、知识源、能力边界完全不同，评审时勿混。

4. 路由与判定

4.1 判定顺序（两端一致）

① 越界拦截          → 非本产品范围 / 违规诉求
② 能力未开放         → 本期未开放的写操作，给手动入口
③ 1.1 新增意图       → 上架 / 下架 / 改价 / 补货单 / 6 张读卡
④ 经营与订单只读     → 销售额 / 订单量 / 经营概览
⑤ 只读护栏           → 列表句式 + 状态词（如「哪些机器离线了」）→ 走只读查询
⑥ 写操作判定         → 两段式：预览（可编辑）→ 确认执行
⑦ 知识问答（RAG）    → mp_kb 条目检索
⑧ 未命中兜底

顺序即优先级，两个易错点：

  • 只读护栏必须在写判定之前：否则「哪些机器离线了」会被当成操作诉求。
  • 线路限定优先于「全部」：「给南油线路所有机器上架…」同时含「所有机器」——线路更具体，先判线路，否则线路限定被吞掉，会当成「全部 12 台」。
  • 按货道（A1 货道 这种点名）优先于通用批量上架（2026-10-28 定稿 #19·2）：「所有机器的 A1 货道上架百事可乐」同样含「上架 / 所有机器」，若被通用批量分支先命中，货道号会被吞掉、退化成「全部 12 台自动分配位置」。① ③ 内先判货道号，命中即走 W2-d（位置锁定、只留售货机）。
  • 「批量」本身就是一个范围词（2026-10-28 定稿 #19 补，v1.23）：批量 / 一键 / 全量 与 所有机器 / 全部点位 / 每台 / 各台 同等看待，命中即进批量三步向导第 1 步（选商品），机器范围留到第 2 步再选。此前只认后者，导致「批量上架百事可乐」被判成单台场景、反问「要在哪台机器上架商品」，用户再答商品规格（「500ml」）又判成没认出机器，最终落到未命中兜底、一张卡都出不来。只有整句既没范围词、也没点名机器时，才允许反问机器。
  • 经营只读要解析时间范围（2026-10-22 产品反馈：「我输入最近30天的销售额，你给我回复了今日销售数据」）：销售额 / 订单量卡命中④后须解析范围词——最近 / 近 N 天、N 天内 → 近 N 天口径；本月 / 这个月 / 当月 → 本月口径；不带范围词才默认今日。卡片标题与行标签同步带范围（如「📊 销售数据 · 近 30 天」），接口 range 参数同步（30d / month / today）。
  • 订单卡对齐线上列表（2026-10-28 定稿 #15）：最近订单 / 异常订单卡（两端共用 cardOrderList）行内不显示支付方式；异常订单行＝机器名 + 机器编号（不展示商品名）＋异常原因短语（不展示「类型：长解释」）＋「已超过 xx 小时」（≥24 小时标红）。R2 订单明细卡 / 选单列表的支付 / 状态列一并去掉（§6.2）。

4.2 只读护栏

命中「列表句式 + 状态词」时判为只读查询，不进入写流程。价格类只读需同时命中 价格|售价|定价|单价|多少钱|价目，且不含 改|调|设|修改——含了就是写操作。

5. 写能力详设

写操作统一走两段式：① 预览（表格内可直接改）→ ② 点击确认才调用写接口。只对改动过的行签发 confirm_id；取消则什么都不发生。

5.1 上架商品（A1 · 卡片 W1 / W1-b）

触发：「帮我在南油文化广场上架康师傅碱性水」

字段：商品名称 / 价格（元，可改） / 补货量。 - 价格默认取商品库自身价，必须可改；改动行加蓝框 - diff 区（2026-10-22 定稿 #12）＝标题直接叫「价格改动」，下面逐行列出改价商品与改前 → 改后价格（如「慕蓝卡苏打水 柠檬味　¥4.00 → ¥4.50」）；没有价格改动时整块不展示（不再保留「将上架 N 项」标题——件数由按钮「确认上架（N 项）」承担，价格与件数表格里已经有了） - 补货量默认值＝商品箱规 × 1.5（四舍五入取整，2026-10-16 产品确认：对齐现有系统「添加商品后补货数带值」的行为，保留该默认；PC 端箱规列随行展示）。⚠ 箱规为 0 或未配置 → 补货量与箱规列都展示 0，不做其他兜底。补货量可逐项手改；注意与 W5 补货单口径（补货量＝最大库存 − 现存，见 §5.6）区分，两卡口径不同 - 不显示库存与商品ID——商品尚未上架，两项均无意义 - 「＋ 添加商品」呼出 P1 弹层

5.5 生成补货单（B2 · 卡片 W5）

入口与机器范围（2026-10-28 产品反馈，定稿 #16）：机器范围不能由 AI 默认代选。

  • 未点名机器（「生成补货单」/ 技能清单点「补货单」）→ 先出**「选择补货机器」卡**：候选＝当前缺货的机器，按缺货率倒序，逐台给机器编号 + 名称 + 缺货率 + 状态；默认勾中缺货率 ≥30% 且可补的机器，勾选后才进 W5 确认卡

  • ⚠ 底部「生成结构」说明区里的 100-1 / 100-2 是子单号（主单号 − 序号），不是机器编号，不能替代机器明细

字段：商品名称 / 缺货数 / 缺货箱数 / 补货量。不显示价格与商品ID——补货下单只看「缺多少、缺几箱、补多少」，价格用不到。

  • 箱规（N 件/箱）放名称下方副行；缺货箱数 = 缺货数 ÷ 箱规，按「N 箱 M 件」展示
  • 补货量口径（2026-10-16 产品裁决）：不用算法建议量，补货量一律 ＝ 最大库存（后台「补满」配置值）− 现存；缺货数同口径，因此「缺货数」与「补货量默认值」相等
  • ⚠ 最大库存的字段归属（2026-10-16 代码复核）：后台「补满」配置值没有独立配置表，就是货道字段 machine_aisle_info.default_goods_stock（MachineAisleInfo.defaultGoodsStock）；补货明细里的 maxStockQty 只是对该字段的快照，公式 diffStock = 默认库存 − 现有库存 与之一致
  • ⚠⚠ 必须取 analysis 侧真实值：micro-service-data 的旧实现按销量补货时用硬编码 goodsStock * 2（ReplenishmentDataServiceImpl.java:646），与真实 defaultGoodsStock 会算出两个结果。AI 一律走 micro-service-analysis 取 defaultGoodsStock 真实字段，不得沿用 goodsStock * 2
  • 补货量仍可逐项手改（改动行加蓝框，diff 区列「已手改 N 项」），只是不再有算法建议兜底
  • 原「按销量 / 按补满库存」模式二选一（.seg）取消，W5-a / W5-b 合并为 W5；原「静态柜固定按销量」的约束一并移除（不再有模式可切）

生成结构：一主多子——一次生成一张主单（masterId），每台机器挂一条子单（子单号＝主单号-序号），禁止逐台循环调用（会出多张主单）。

⚠⚠ 跨仓拦截有前提条件（2026-10-16 代码复核，被补上的遗漏）：跨仓校验位于 ReplenishmentListMasterServiceImpl.java:439-449，但外层套了 ispReplenishSku 开关—— if (Objects.nonNull(masterView.getIspReplenishSku()) && masterView.getIspReplenishSku() && orgIds.size() > 1) { …ispStockHouseInfoList.size() > 1 → throw「补货机器关联多个车线路仓，请和仓管确认，按车线路仓分开提交」 } 即：仅当该主单启用 ISP 服务商补货时才校验。普通运营商（未开 ISP）选了跨仓的多台机器，会直接合成一张主单且不报错。

⚠⚠ 「铺货 N 台」需新增接口（2026-10-16 代码复核）：现有 GoodsSoldController.soldMachineNumber 取的是 machine_sold_group_day_sku 的 COUNT(DISTINCT machine_id)，＝有销售记录的机器数，不是铺货数（没卖过的机器不计）。真正的铺货口径（machine_aisle_info 关联 goods_sku_info 反查）在 GoodsSoldMapper.xml:280+，挂在 GoodsDisplay 服务上，GoodsSoldController 未暴露。 结论：口径保留（§12.1 已定稿 5），但实现方式改为新增接口，由 ca-api 编排前先落接口；接口未就绪前 R5 该列留空并标注「暂不可用」，不得用「卖过的机器数」顶替（会低估铺货规模）。

6.6 R6 离线原因（C9）

口径：原因取自 monitor_fault_records（fault_type='machine_offline'）故障记录，处理建议文案取自 nacos 配置（现为「机器离线时间超过阀值，请检查网络」，MonitorFaultRecordServiceImpl.java:130-131）；并标注来源与时间。无记录时给「暂无原因记录，建议查硬件状态 / 提交工单」。

⚠⚠ 2026-10-16 代码复核修正：原写「预警通知或操作日志」——machine_online_record 表只有 id / machine_id / online_status / msg_protocol / gmt_created，没有离线原因字段，「操作日志」这个数据源不存在。若按旧口径接，R6 会拿不到数据。 ⚠ 2026-10-16 第二轮收口：上一版把「预警通知」留作第二个来源，但它同样未被核过（没有对应的表 / 接口证据），属于与上一条同类的「写进结论却没核实」问题。
本期只保留已核实的一个来源 —— 故障记录表；卡片「来源」列只写「故障记录」。「预警通知」能否作为补充来源转入 §12.2 第 4 条待确认，核到证据后再加回卡片，不得先写进结论。

本场景差异：主按钮「加入卡片」；现有为单选一台，本场景改多选以支持批量上下架；已在本卡的机器置灰；列表顶部给全选。 校验前移 · 机型级（2026-10-16 产品反馈：「这种校验不应该在选择机器的时候就直接校验吗」）：机型不支持上架的机器在选择弹层里直接置灰、标注「⛔ 不可上架：不支持在该机型售卖」，checkbox 禁用、不可勾选、不进全选——机型级拦截在选择机器阶段就挡掉；「全部机器 / 按线路」范围不经过弹层，仍可能带入，执行后由 W6 结果卡逐台透传原因兜底（见 §5.2「校验前移」）。⚠ 客户文案不出现「后端校验拦截」这类实现细节（2026-10-16 产品反馈）：失败原因只说业务语义，拦截发生在哪一层属内部信息，不进卡片与弹层文案（同理适用于 P1 商品级置灰原因与 W6 失败原因的透传文案）。 下架场景过滤（2026-10-22 定稿 #12）：W3 内呼出 P2 时只列出已铺该商品的机器——没有该商品的机器不出现在弹层里（没铺货无从下架）；上架场景（W2-c）不适用此过滤。

8. 统一设计原则

以下 19 条是 1.1 全部卡片的共同口径，评审新卡片时按此逐条核对。

# 原则 口径
1 统一字段 商品名称 · 价格 · 库存 是基础项；商品ID 按场景取舍——上架 / 下架卡不显示（商品还没上架，ID 对运营商无意义），补货卡也不显示（改看箱规），改价 / 订单明细卡保留
2 库存列取舍 按「这个场景有没有库存可言」判断：上架＝没有；下架＝显示现有库存，且按机型说清楚处置结果（智能柜「将清空 N 件」/ 售货机「将停售 N 件，库存保留」）；改价＝显示现存；补货＝显示缺货数 / 缺货箱数。
⚠ 2026-10-16 修正：原统一写「将清空」与 §5.3 冲突（售货机不清库存），详见 §8 原则 10
3 价格可编辑 上架卡价格默认取商品库价但必须可改；改动行蓝框高亮，diff 区＝标题「价格改动」+ 逐行「商品 改前 → 改后」（2026-10-22，无改动整块不展示）
4 状态文案 一律用文字「成功 / 失败」，禁止 ✕ ✓；失败原因放名称下方红色副行，机器级与商品级分开标「对象」
5 补货卡字段 不显示价格与商品ID；只讲缺货数 / 缺货箱数 / 补货量；手机端箱规放副行、PC 端提为列；缺货箱数＝缺货数 ÷ 箱规；补货量＝最大库存（补满配置值）− 现存
6 补货量口径 不做系统建议量、不由算法推荐，补货量一律＝最大库存（补满配置值）− 现存，逐项可改。原 .seg「按销量 / 按补满库存」二选一已取消（2026-10-16 裁决 6）；静态柜「仅支持按销量」的旧约束不再适用于 AI 卡片
7 两段式写卡 预览（可编辑表格 + 改动 diff）→ 确认才调写接口；只对改动行签发 confirm_id；取消什么都不发生
8 校验与失败 AI 侧不重写校验：适用机型、建模、价格区间、库存上下限全部由后端判定，卡片只负责标红 + 原样透传原因。⚠ 机型 / 建模类校验在选择阶段前置拦截（P2 机器弹层机型置灰、P1 商品弹层商品置灰，见 §7），W6 结果卡透传作兜底（2026-10-16）
9 多台执行 统一 ca-api 单机循环；结果卡必须逐台列出成功 / 失败与原因，不得整批报失败、不得静默跳过
10 下架处理 按机型分两套：智能柜＝移除 + 库存清零；售货机＝货道停售（不清空、不换商品，is_sale_enabled='N'）。
⚠ 2026-10-16 代码复核修正：原「换默认商品」为误，见 §5.3
11 上架位置 按机型分两套：售货机＝货道（逐个指定）；智能柜＝层。位置 chip 带「▾」＝可点选，呼出选择弹层列全部层 / 货道（已铺标「已有：商品名」、空闲标「空闲」，售货机带最大 / 现存），点选回填且副行联动（2026-10-22 定稿 #13）。批量上架同样可点选（2026-10-28 定稿 #19：第 3 步逐台按机型给位置，智能柜默认第 1 层、售货机默认下一个空闲货道，预填后仍可点选改；旧口径「批量不逐台指定、各机自动分配」作废）
12 读卡操作位 读卡不带「确认执行」；只在确有明确下一步且是该数据的自然延续时才给按钮（如补货记录 → 生成补货单）；不硬凑动作，没有下一步就不给按钮区
13 结果卡闭环 成功 / 失败两个动作都要有下文，同源同批，成功台数 + 失败台数 = 命中总数
14 说明行 卡片底部灰色说明行只承载本条数据的口径（能查多久、数据来源、默认给什么）；不写「你可以接着问我…」这类引导话术
15 移动端不做导出 一律不提供「导出 / 下载」；列表在卡内滚动看全量。需要留存（对账 / 存档）引导到 PC 端管理后台
16 多选必给全选 凡逐行勾选的表格 / 列表，列头（表格）或列表顶部（弹层）必须给全选，不允许只能逐行点。三态：表格用方框 ☑ / ▣ / ☐，弹层用圆形 ◉ / ◍ / ○。选中数实时回显到 diff 区与按钮文案
17 卡片宽度 小程序端 300px（375 屏内可用宽约 308px）；PC 端按抽屉宽度放开（720px 抽屉内约 630px），表格列可加宽
18 空状态 读卡查不到数据时不给空表（空表＝像坏了）。统一走 emptyCard()：图标 + 一句「现在是什么情况」+ 一句为什么（时间范围 / 筛选条件 / 排查建议）。有自然下一步才给按钮，否则只给文案
19 加载 / 执行中态 取数过程走卡片级骨架屏 loadingCard()，只给行骨架、不假装有数字；写操作执行中统一用按钮态「⏳ 执行中…」+ 状态标签同步，执行期间禁用重复提交

20 「批量上架」不出卡（2026-10-28 产品反馈，附真机截图：「批量上架百事可乐」没有对应的卡片交互） 「批量 / 一键 / 全量」本身就是范围词，与「所有机器 / 全部点位 / 每台 / 各台」同等处理——命中即进 W2 三步向导第 1 步（选商品），机器范围留到第 2 步再选。此前范围词只认后者，「批量上架百事可乐」被判成单台场景去反问「要在哪台机器上架商品」，用户回商品规格（「500ml」）又被判成没认出机器 → 未命中兜底，一张卡都出不来。只有整句既无范围词、也未点名机器（如「上架百事可乐」）才允许反问机器。详见 §4.1 / §5.2
