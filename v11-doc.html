1. 背景与目标

1.1 背景

1.0 期 AI 助手已上线，能「说」能查，但能做的动作很少。我们从 654 条运营商真实问话里做了归因，发现两类结构性问题：

  • 能力缺口：问话里有 6% 是明确的执行诉求（「帮我在南油文化广场上架康师傅碱性水」），1.0 只能答不能做。
  • 查询缺口：TOP4 问法（今日销售额 128 / 哪些机器缺货 128 / 查我的机器 73 / 怎么新增商品 44）合计占 57%，其中**「怎么新增商品」这类教学诉求**占了很大比重——因为系统里做得出来，但用户找不到入口。

⚠ 归因结论：TOP4 的高问话量主要由欢迎卡 4 个快捷按钮驱动（入口驱动），不全是未满足需求。因此本期不做「欢迎卡加经营数据卡」，而是把力气花在真正缺的能力上（详见 §3.4）。

1.2 本期目标

目标 落地方式
把高频执行诉求变成可代做 新增写能力 4 项：商品上架 / 下架 / 跨机器批量改价 / 生成补货单
把高频查询诉求补齐 新增读能力 6 张卡：补货记录 / 订单商品明细 / 按销售额反查机器 / 支付方式拆分 / 商品维度销售 / 离线原因
补知识库缺口 qa 补条目 3 项：故障排查 SOP / 商户工单兜底 / 客服管理（按载体端分路径）
把能力搬上 PC 运营商 PC 后台同一套能力，卡片字段一次给全（大屏不再折叠为副行）

1.3 边界（本期不做，见 §3.4 逐条理由）

  • 欢迎卡新增经营数据卡（移除：入口驱动，非未满足需求）
  • 音量设置写能力、缺货率门槛写能力（引导，不做写）
  • 商品库新增商品（涉及平台审核流与商品建模，无法对话闭环）
  • 远程开门（安全风险，直接触发物理门锁）
  • 技术 API / 回调问答、企业内部流程、视频监控查看、改名记录查询

2. 端与定位

2.1 三端定位

端 使用者 形态 本期定位
小程序端 运营商（客户） 移动端 375 屏，悬浮球进对话页 能说也能做：知识问答 + 只读查询 + 写操作（两段式）
运营商 PC 后台 运营商（客户） PC 后台右下角悬浮球 → 右侧抽屉（720px） 与小程序端同一套能力；因屏宽更大，卡片字段一次给全
公司内部 OS 后台 内部员工 OS 后台抽屉 本期不变：只问答与只读查询，不执行任何操作

2.2 为什么 OS 内部端本期维持「只说不做」

内部 OS 端的定位是内部口径问答（知识源 os_kb + 产品手册 FAQ），使用者是公司员工，操作类诉求有既定的后台流程与权限体系承接。把它开放成可执行，会引入内部越权与审计口径两类新问题，不是本期要解的事。

⚠ 澄清：本期说的「PC 端」指运营商 PC 后台，不是公司内部 OS。两者形态相似（都是右下角悬浮球 + 右侧抽屉），但使用者、知识源、能力边界完全不同，评审时勿混。

2.3 编号说明（避免评审混淆）

编号体系 例子 含义

3.3 配套要求（不单列排期）

B7 能力配套：NLU 泛化 + 机器点名 / 上下文（原 B7 + B8 合并）。包含：

  • 口语归一化：缺货 ↔ 空货、离线 ↔「高线」、营业额 ↔ 实收、今天撞的多不多 等（约 90 条）
  • 纯点位名 / 编号开场：如「雀妹棋牌（51890784）」直接开场（61 条）——并入 R1 与机器选择交互

⚠ 风险：ca-api 不在本代码库，NLU 泛化与 mp_kb 结构无法在代码层面核对，只能核对到数据源与前端卡片缺口。该配套项随相关能力一并交付，需后端确认口径。

4. 路由与判定

4.1 判定顺序（两端一致）

① 越界拦截          → 非本产品范围 / 违规诉求
② 能力未开放         → 本期未开放的写操作，给手动入口
③ 1.1 新增意图       → 上架 / 下架 / 改价 / 补货单 / 6 张读卡
④ 经营与订单只读     → 销售额 / 订单量 / 经营概览
⑤ 只读护栏           → 列表句式 + 状态词（如「哪些机器离线了」）→ 走只读查询
⑥ 写操作判定         → 两段式：预览（可编辑）→ 确认执行
⑦ 知识问答（RAG）    → mp_kb 条目检索
⑧ 未命中兜底

顺序即优先级，两个易错点：

  • 只读护栏必须在写判定之前：否则「哪些机器离线了」会被当成操作诉求。
  • 线路限定优先于「全部」：「给南油线路所有机器上架…」同时含「所有机器」——线路更具体，先判线路，否则线路限定被吞掉，会当成「全部 12 台」。

4.2 只读护栏

命中「列表句式 + 状态词」时判为只读查询，不进入写流程。价格类只读需同时命中 价格|售价|定价|单价|多少钱|价目，且不含 改|调|设|修改——含了就是写操作。

4.3 兜底

场景 处理
越界 「超出能力范围」+ 说明能做什么
本期未开放 明确「暂不支持」+ 给对应页面的手动入口
知识未命中 换说法提示；连续未命中引导咨询售后客服
写操作失败 逐项列出失败原因（原样透传后端），不得整批报失败
无「转人工」 统一引导「咨询售后客服」，不承诺时效

5. 写能力详设

写操作统一走两段式：① 预览（表格内可直接改）→ ② 点击确认才调用写接口。只对改动过的行签发 confirm_id；取消则什么都不发生。

5.1 上架商品（A1 · 卡片 W1 / W1-b）

触发：「帮我在南油文化广场上架康师傅碱性水」

字段：商品名称 / 价格（元，可改） / 补货量。 - 价格默认取商品库自身价，必须可改；改动行加蓝框，diff 区列「价格改动 N 项（改前 → 改后）」 - 不显示库存与商品ID——商品尚未上架，两项均无意义 - 「＋ 添加商品」呼出 P1 弹层

上架位置按机型分两套：

机型 位置口径 卡片表现
智能柜 层（无货道概念） 点层号可改
售货机 货道，逐个指定 每商品一行给货道 chip（默认分配空闲货道），点开可改选；副行给「最大 N · 现存 M」

售货机最大库存：机器侧配置项，可售库存不可大于最大库存；超出时标红拦截。

5.2 批量上架（A1 · 卡片 W2-a / W2-b / W2-c）

三张卡共用同一套商品行，仅机器选择区不同，顶部 .seg 切换（默认「全部机器」）：

卡 范围 表现
W2-a 全部机器 范围只写「全部 N 台」，不区分在线 / 离线台数
W2-b 按线路 kv 行是下拉（线路 + 台数），下方 chips 预览该线路机器、可切换
W2-c 自选 chips 逐个列出已选机器（带 ✕ 可删）+「＋ 添加机器」（呼出 P2）；diff 区列出全部机器编号，确认前防选错

批量不逐台指定货道 / 层（各机货道不同，一张卡里无法逐个指定），按各机自动分配；要精确指定货道用单台卡 W1 / W1-b。

  • 离线机器也支持上架（2026-10-16 产品裁决）：AI / 前端不做在线状态门槛，是否可上架由后端判定；卡片范围只写「全部 N 台」，不区分在线 / 离线台数，成败一律由后端校验结果透传（失败原因原样展示在 W6）
  • 商品库按机型交集出（2026-10-16 产品裁决）：P1 弹层在批量场景取这批机器机型的交集，交集外的商品直接不出现（能提前挡掉「选完即失败」）；弹层标题写明交集、下方给一行过滤说明。单台上架＝交集退化为该机机型，与现有「添加商品」页一致

5.3 下架商品（C8 · 卡片 W3）

字段：机器 / 商品名称 / 价格 / 库存 / 勾选。不显示商品ID（与上架一致）；库存列保留——要告诉用户将清掉多少件。

  • 默认全选、可逐台取消，未勾选不提交；列头「全选」一键全选 / 再点全不选，部分选中显示半选态
  • 主按钮用橙色（与改价区分）

下架处理按机型分两套：

机型 处理
智能柜 移除该商品、库存清零
售货机 把该货道换成默认商品（不清空，货道继续售卖）

5.4 批量改商品价格（C2 · 卡片 W4）

卡片四字段：商品名称 / 商品ID / 当前价 / 目标价（ID 保留——改价须精确到具体商品），另带库存列与命中机器数。

  • 跨机器同商品批量改价属新粒度，与单机改价并存、不合并
  • 表格一行一商品（目标价 > 0）
  • 命中台数可展开到机器层级（2026-10-16 产品裁决）：卡内加「命中机器明细」块，按商品分组逐台列出编号 + 名称 + 现价；默认收起（只占一行），点标题展开，机器多时展开区卡内滚动（限高 186px）、随时可收起。PC 端「命中机器」列显示为「N 台 ▾」，点列里的台数即展开

5.5 生成补货单（B2 · 卡片 W5）

字段：商品名称 / 缺货数 / 缺货箱数 / 补货量。不显示价格与商品ID——补货下单只看「缺多少、缺几箱、补多少」，价格用不到。

  • 箱规（N 件/箱）放名称下方副行；缺货箱数 = 缺货数 ÷ 箱规，按「N 箱 M 件」展示
  • 补货量口径（2026-10-16 产品裁决）：不用算法建议量，补货量一律 ＝ 最大库存（后台「补满」配置值）− 现存；缺货数同口径，因此「缺货数」与「补货量默认值」相等
  • 补货量仍可逐项手改（改动行加蓝框，diff 区列「已手改 N 项」），只是不再有算法建议兜底
  • 原「按销量 / 按补满库存」模式二选一（.seg）取消，W5-a / W5-b 合并为 W5；原「静态柜固定按销量」的约束一并移除（不再有模式可切）

生成结构：一主多子——一次生成一张主单（masterId），每台机器挂一条子单（子单号＝主单号-序号），禁止逐台循环调用（会出多张主单）。

约束：合并的多台机器须同属一个车线路仓，跨仓时按仓分开提交（后端直接报错拦截）。

5.6 批量执行结果与成功明细（W6 / W6-b）

结果卡必须闭环：失败可重试、成功可展开明细，两者同源同批（成功台数 + 失败台数 = 命中总数），不允许只报一边。

卡 内容 动作
W6 结果卡 成功 N 台 / 失败 M 台 + 失败项逐条列原因 「查看成功明细」→ W6-b；「重试失败 M 台」
W6-b 明细卡 逐台列出成功机器（编号 + 机型） 只读卡，不带确认执行；仅「返回执行结果」
  • 状态列一律用文字「成功 / 失败」，不用 ✕ ✓
  • 失败原因放名称下方副行（红色），机器级与商品级分开标「对象」
  • 原因文案直接透传后端原文

6. 读能力详设

读卡不带「确认执行」按钮；只在确有明确下一步、且是该条数据的自然延续时才给按钮。

6.1 R1 补货记录（B1）

口径：① 最近一个月补过货的机器 → ② 各自补货次数 → ③ 未补货时长从长到短倒序。

  • 行可勾选，默认勾中 7 天以上未补货的机器；表头全选一键全选 / 再点全不选，部分选中半选态
  • 选中数实时回显到 diff 区与底部按钮（「为这 2 台生成补货单」）
  • 底部直连 W5 补货单卡，形成「查 → 补」闭环
  • 说明行：最多可查近 180 天的补货记录

6.2 R2 订单商品明细（B3）

字段：商品名称 / 商品ID / 单价 / 数量 / 小计 + 合计行。用途：智能柜「拿了货没扣到钱」的资损核对。

6.3 R3 按销售额反查机器（C3）

支持阈值筛选与排序（「低于 700 的」「上个月低于 1000 的」）；结果可关联补货状态，接着生成补货单。

6.4 R4 销售额支付方式拆分（C4）

口径：默认给合计，用户要求时才拆分。拆分维度：支付方式 / 金额 / 笔数 / 占比 + 合计行。

6.5 R5 商品维度销售额（C7）

字段：商品名称 / 商品ID / 单价 / 销量 / 销售额 + 铺货机器数；支持限定「所有在线机器」范围。

6.6 R6 离线原因（C9）

口径：原因取自预警通知或操作日志，并标注来源与时间；无记录时给「暂无原因记录，建议查硬件状态 / 提交工单」。

这是纯只读卡——不给「查硬件状态 / 远程重启」按钮：卡内已在展示状态，再点「查硬件状态」是循环跳转；重启属另一个能力，用户直接问即可。

7. 选择弹层：挑商品 / 挑机器

⚠ 两端容器不同、内容同一份：手机端 375 屏只能走底部半屏弹层；PC 端不弹半屏——改成在触发它的那张卡下方接一张内联表（.pc-inline），每行右侧一个行内按钮「加入 / 选这台」，不占满屏、不打断右侧面板（见 §9.1）。两端的列表内容、全选、置灰、数量角标逻辑完全一致。

7.1 P1 添加商品（W1 / W2 内「＋ 添加商品」）

沿用现有「添加商品」页骨架：搜索（名称 / 条码）+ 扫码、分组标题（私有商品库 · 仅当前机型可售）、行结构（缩略图 + 商品名 + 品牌规格 + 橙色价格 + 适用机型）、圆形勾选、底栏数量角标。

本场景差异： 1. 主按钮**「加入卡片」**——弹层只往卡片加项，无下一步 2. 带价入卡后默认取商品库价、可改 3. 已在本卡的商品置灰（不参与全选） 4. 列表顶部「全选」一键全选 / 取消全选，部分选中半选态 ◍，已选数回显在右侧

7.2 P2 添加机器（W2-c / W3 内「＋ 添加机器」）

沿用现有「选择机器」页骨架，行结构＝「(编号) 名称 + 地址全称」（地址完整展示、可换行不省略，按需求不展示机器图片）。

本场景差异：主按钮「加入卡片」；现有为单选一台，本场景改多选以支持批量上下架；已在本卡的机器置灰；列表顶部给全选。

8. 统一设计原则

以下 17 条是 1.1 全部卡片的共同口径，评审新卡片时按此逐条核对。

# 原则 口径
1 统一字段 商品名称 · 价格 · 库存 是基础项；商品ID 按场景取舍——上架 / 下架卡不显示（商品还没上架，ID 对运营商无意义），补货卡也不显示（改看箱规），改价 / 订单明细卡保留
2 库存列取舍 按「这个场景有没有库存可言」判断：上架＝没有；下架＝显示现有库存（并标「将清空 N 件」）；改价＝显示现存；补货＝显示缺货数 / 缺货箱数
3 价格可编辑 上架卡价格默认取商品库价但必须可改；改动行蓝框高亮，diff 区列改动前后
4 状态文案 一律用文字「成功 / 失败」，禁止 ✕ ✓；失败原因放名称下方红色副行，机器级与商品级分开标「对象」
5 补货卡字段 不显示价格与商品ID；只讲缺货数 / 缺货箱数 / 补货量；手机端箱规放副行、PC 端提为列；缺货箱数＝缺货数 ÷ 箱规；补货量＝最大库存（补满配置值）− 现存
6 补货量口径 不做系统建议量、不由算法推荐，补货量一律＝最大库存（补满配置值）− 现存，逐项可改。原 .seg「按销量 / 按补满库存」二选一已取消（2026-10-16 裁决 6）；静态柜「仅支持按销量」的旧约束不再适用于 AI 卡片
7 两段式写卡 预览（可编辑表格 + 改动 diff）→ 确认才调写接口；只对改动行签发 confirm_id；取消什么都不发生
8 校验与失败 AI 侧不重写校验：适用机型、建模、价格区间、库存上下限全部由后端判定，卡片只负责标红 + 原样透传原因
9 多台执行 统一 ca-api 单机循环；结果卡必须逐台列出成功 / 失败与原因，不得整批报失败、不得静默跳过
10 下架处理 按机型分两套：智能柜＝移除 + 库存清零；售货机＝换成默认商品（货道继续售卖）
11 上架位置 按机型分两套：售货机＝货道（逐个指定）；智能柜＝层。批量不逐台指定，走各机自动分配
12 读卡操作位 读卡不带「确认执行」；只在确有明确下一步且是该数据的自然延续时才给按钮（如补货记录 → 生成补货单）；不硬凑动作，没有下一步就不给按钮区
13 结果卡闭环 成功 / 失败两个动作都要有下文，同源同批，成功台数 + 失败台数 = 命中总数
14 说明行 卡片底部灰色说明行只承载本条数据的口径（能查多久、数据来源、默认给什么）；不写「你可以接着问我…」这类引导话术
15 移动端不做导出 一律不提供「导出 / 下载」；列表在卡内滚动看全量。需要留存（对账 / 存档）引导到 PC 端管理后台
16 多选必给全选 凡逐行勾选的表格 / 列表，列头（表格）或列表顶部（弹层）必须给全选，不允许只能逐行点。三态：表格用方框 ☑ / ▣ / ☐，弹层用圆形 ◉ / ◍ / ○。选中数实时回显到 diff 区与按钮文案
17 卡片宽度 小程序端 300px（375 屏内可用宽约 308px）；PC 端按抽屉宽度放开（720px 抽屉内约 630px），表格列可加宽

为什么补货单要加「可售库存 / 最大库存」：小程序端是补货员在机器旁按单补货，主要看缺货数；PC 端是仓管 / 运营在后台按单备货，必须知道「现在还剩多少（可售库存）」和「最多能放多少（最大库存）」，否则备货量与货道容量对不上。

实现上两端共用同一份卡片与路由代码（mp_v11_app*.js），PC 端仅在外壳与宽度上覆盖（pc_v11_extra.css + pc_v11_adapter.js），以 PC_WIDE 开关控制「副行 → 列」与新增字段的输出。因此卡片口径改动两端天然同步，不存在漂移风险。

11. 验收标准

11.1 功能验收

  1. 写能力 4 项（上架 / 下架 / 批量改价 / 补货单）在小程序端与 PC 端均能完成「预览 → 确认执行」闭环；取消不产生任何副作用。
  2. 读能力 6 张卡均能按代表问法命中出卡，字段与 §6 一致。
  3. 补货单结构：一次生成一张主单 + 每台机器一条子单；跨仓被拦截并给出明确错误。
  4. 结果卡闭环：批量执行后成功 + 失败 = 命中总数；失败项可重试，成功项可展开明细。
  5. 机型差异：下架（智能柜移除 / 售货机换默认商品）、上架位置（层 / 货道）按机型正确分流。
  6. qa 补条目 3 项入库后能被对应问法命中；客服管理条目按载体端分路径返回正确入口。

11.2 交互与口径验收

  1. 所有写卡为两段式，只对改动行签发 confirm_id。
  2. 全部卡片状态列用文字不用符号；失败原因逐项透传，不整批报失败。
  3. 凡逐行勾选的表格 / 列表都有全选控件且三态正确；选中数回显到按钮文案。
  4. 读卡不带确认执行；无明确下一步就不给按钮区；无循环跳转按钮。
  5. 卡片底部说明行只有口径，无「你可以接着问我…」类引导话术。
  6. 移动端与 PC 端均不提供导出 / 下载。

11.3 回归验收

  1. 1.0 既有链路（机器列表 / 状态筛选 / 经营只读 / 停售 / 知识问答 / 越界兜底 / 未命中兜底）全部不受影响。
  2. 两端原型冒烟：小程序端 78 项断言全通过；PC 端 67 项断言全通过（含「副行提为列」与「PC 列不得出现在小程序端」双向断言）。
  3. 布局无溢出：卡片、表格、行内元素在两端均无横向溢出。
